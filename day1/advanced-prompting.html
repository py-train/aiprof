Advanced Prompting

System prompts, structured output, iteration, and knowing when to trust the answer.

The conversation

The conversation has a hidden layer

Most AI chat interfaces show you one box. Under the hood, there are two:

LayerWho writes itWhat it does
System promptDeveloper or power user — set onceEstablishes identity, rules, output style, and constraints before the conversation starts
User messageYou — each turnThe actual request, question, or task

System:

"You are a professional business writing assistant. Respond only in formal English. Always structure answers with a summary paragraph followed by bullet details."

User:

"Draft a status update for the Q3 budget review."

The system prompt is the model's job description. Write it the way you'd brief a very capable new hire on their first day.

System prompts

Four ingredients of a well-written system prompt

1. Role / Identity

Who the model is playing. Grounds tone and vocabulary.

"You are a senior financial analyst at a global professional services firm."

2. Constraints

What it must not do. Prevents drift.

"Do not provide legal advice. Do not fabricate data. If you are uncertain, say so."

3. Output format

How answers should be structured by default.

"Always respond in this format: [Executive Summary], [Key Points], [Recommended Next Steps]."

4. Tone and audience

Register and formality level.

"Write for a non-technical executive audience. Use plain English. Avoid acronyms unless you define them."

You don't need all four every time. Identify which ones the task actually needs — then add only those.

Personas

Giving the model a role to play

When personas help

  • • They prime the model to frame responses the way an expert would
  • • They set vocabulary, tone, and default assumptions
  • • They help apply the right lens to an ambiguous request

"You are a skeptical risk consultant." → The model will probe for weaknesses, not just validate.

When personas don't help

  • • The model doesn't become the person — it can't access their private knowledge
  • • A persona won't fix a bad question or compensate for missing context

"You are Warren Buffett. What should I invest in?" → Still just the model's training data, in Buffett's style.

The honest mental model

A persona changes the angle, not the underlying capability. It's like telling a consultant "put on your risk hat for this" — useful framing, not a skill transplant.

Structured output

If you need a specific format, say so explicitly

By default, models give conversational prose. If you need something machine-readable or consistently structured — you have to ask for it.

Unspecified

"Summarise the risks in this document."

→ Three paragraphs of flowing text. Hard to paste into a report template.

Specified

"Summarise the risks. Return a markdown table: Risk, Likelihood (High/Medium/Low), Recommended Action."

→ A clean, copy-pasteable table every time.

Common formats to request

  • • Markdown table — for structured comparisons
  • • Numbered / bullet list with defined hierarchy
  • • JSON with defined fields — for developers piping output into systems
  • • Document section structure — "use headings: Background, Findings, Recommendations"
  • • Fill-in-the-blank template — give the template, ask the model to complete it

Structured output is not about being fancy — it's about getting output you can actually use without reformatting it yourself.

Optional depth

From prose to JSON — the same task, two outputs

Without format instruction

"Extract the key action items from this meeting transcript."

Output: A paragraph listing things that came up in the meeting, loosely worded.

This output can feed directly into a project tracker, spreadsheet import, or downstream app — no manual reformatting.

With format instruction

"Extract action items. Return a JSON array. Each item: owner (string), task (string), due_date (string or null), priority (High / Medium / Low)."

[

{"owner": "Sarah", "task": "Send revised proposal", "due_date": "2025-10-15", "priority": "High"},

{"owner": "James", "task": "Book venue for workshop", "due_date": null, "priority": "Medium"}

]

Prompt failures

When the output is wrong, here's where to look

Failure typeWhat it looks likeFix
Too vagueModel guesses what you wanted and guesses wrongAdd context: who is this for, what decision does it support?
Missing contextModel uses generic knowledge when you needed specificPaste in the relevant document, data, or background
Conflicting instructionsModel compromises between two things you asked forPick one priority; don't ask for "concise but comprehensive"
No exampleModel uses a different structure or style than you imaginedShow it one example of the output you want

The iteration loop

  1. 1. Run the prompt
  2. 2. Identify which failure type applies
  3. 3. Fix that — not everything at once
  4. 4. Re-run and compare

Prompt debugging is a skill, not a mystery. Each failure tells you something specific about what the model was missing.

Anti-patterns

Mistakes that reliably produce bad output

"Do everything at once"

"Write a full market analysis covering competitors, regulatory risks, pricing strategy, and go-to-market timeline."

→ The model covers everything shallowly. Break it into separate prompts.

"Be smart about it"

"Use your best judgment to decide the format and length."

→ You'll get something. Whether it's what you needed is luck. Specify.

"Keep it short but include everything"

"Write a brief but comprehensive summary."

→ Brief and comprehensive conflict. Pick a word count or required sections — not both adjectives.

"Assume it remembers"

(New session) "Continue where we left off."

→ Every session starts fresh. Relevant prior context must be re-supplied.

Evaluation

"It looks good" is not a quality check

CheckAsk yourself
AccuracyAre the facts, figures, and names correct? Can I verify the critical ones?
CompletenessDid it address everything the prompt asked for? Are there obvious gaps?
FormatIs it structured the way I need it? Does it fit where it's going?
ToneIs the register right for the audience — not too casual, not too stiff?
SafetyCould anything here cause harm, embarrassment, or legal exposure if used as-is?

High-stakes output

Client-facing, financial, legal → verify facts independently

Internal draft

Trust the structure, spot-check the substance

Purely stylistic

Tone, formatting → safe to trust more freely

AI is a first drafter, not a final approver. You are still the quality gate.

Prompt makeover

One task. Four versions.

Task: Summarise a supplier contract to help a procurement manager decide whether to renew.

Version 1 — Bare minimum

"Summarise this contract."

Generic summary. Dates, parties, payment terms. Nothing about whether to renew.

Version 2 — Add task framing

"Summarise this contract. Focus on anything relevant to a renewal decision."

Better. Highlights renewal clauses and key dates. Still prose — hard to act on directly.

Each version is adding one thing. That's the iteration pattern — a targeted addition, not a full rewrite.

Prompt makeover (contd.)

Adding format, then context

Version 3 — Add format

"Summarise this contract for a procurement manager. Return a table: Topic, Current Terms, Risk Level (High/Medium/Low), Renewal Recommendation."

Structured and actionable. But the model invents risk levels with no criteria.

Version 4 — System context + criteria

System: "You are a contract risk analyst. Flag High risk if terms expose the company to financial liability. Medium if limiting but manageable. Low if standard."

User: "Summarise for renewal decision. Table: Topic | Current Terms | Risk Level | Recommendation."

Consistent risk assessment grounded in clear criteria. Repeatable across 50 contracts.

Each version added one thing. That's the iteration pattern — not a rewrite, a targeted addition.

Habits

It's not about knowing magic words

Three habits that compound over time:

📚

Write for reuse

If you've written a good prompt once, save it. Prompt libraries — even a simple shared doc — let teams build on each other's work instead of starting from scratch.

⬆️

Front-load context

The model reads top to bottom. Put the most important constraints and context at the start — don't bury them after a long preamble.

🧪

Test with boundary cases

Before deploying a prompt for repeated use, test what happens when the input is messy, incomplete, or off-topic. A prompt that breaks on real data is a problem waiting to happen.
